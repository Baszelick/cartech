# CarTech Business Rules

## Company и вход

- `Company.code` обязателен, глобально уникален, нормализуется через trim + uppercase, имеет длину 2–32 и формат `^[A-Z0-9_-]{2,32}$`.
- Пользователь входит по `companyCode`, username и password; UUID `companyId` остаётся внутренним идентификатором связей, scope и JWT.
- Неизвестная/неактивная компания, неизвестный/неактивный пользователь и неверный пароль не раскрываются и возвращают одинаковый `401 Unauthorized`.
- Refresh и `/auth/me` не требуют `companyCode`.
- `GET /company/me` использует только `companyId` из JWT и недоступен до обязательной смены временного пароля.

> Подтверждённые правила целевой доменной модели. Неопределённые правила явно отмечены как открытые вопросы.

## 1. Приёмка автомобиля

- Приёмка является бизнес-операцией, а не отдельной хранимой сущностью.
- Одна операция может создать один или несколько автомобилей.
- Операция выполняется атомарно в одной транзакции.
- Каждый создаваемый Car получает `companyId`, `ownerLocationId`, `currentSiteId`, `arrivalSiteId`, `createdById`, `arrivedOn`, обязательный `shortVin` и identity snapshot; полный VIN может отсутствовать.
- Для каждого Car создаётся отдельная `Pso` со статусом `PENDING`; все автомобили batch используют общий `arrivedOn`.
- `Pso.deadlineOn` равен `arrivedOn + 3` календарных дня; `completedOn` и `completedById` при создании отсутствуют.
- Для каждого автомобиля создаётся событие `CAR_ARRIVED`.
- Car, Pso и `CAR_ARRIVED` создаются одной транзакцией; Car остаётся в lifecycle `ACTIVE`.
- Заполненный полный VIN уникален в пределах Company.
- Отдельный `arrivalId`, номер автовоза и реестр партий не входят в подтверждённый MVP contract.

## 2. Идентификация автомобиля

- `Car.id` — UUID.
- `shortVin` — обязательный редактируемый рабочий идентификатор: ровно 6 символов `A-Z0-9`, trim + uppercase.
- Совпадения `shortVin` разрешены; API возвращает `hasShortVinDuplicate=true`, если другая машина той же Company имеет такое же значение.
- Текущий автомобиль не считается своим дубликатом; автомобили других Company не учитываются.
- `vin` — необязательный редактируемый полный VIN; поле можно добавить, заменить или очистить через `null`.
- Заполненный VIN нормализуется через trim + uppercase и соответствует `^[A-HJ-NPR-Z0-9]{6,17}$`; `I`, `O`, `Q` запрещены.
- VIN длиной 17 символов считается полностью заполненным; более строгая структурная проверка не выполняется.
- Заполненный VIN уникален только внутри Company; несколько `null` и одинаковые VIN разных Company допустимы.
- `brand`, `model` и `color` хранятся как snapshot-значения в Car.
- `color` может отсутствовать; `brand` и `model` обязательны.
- Отдельные Brand, CarModel и Color entities в целевой MVP-модели отсутствуют.

## 3. Пользователи и доступ

- User принадлежит одной Company.
- Username уникален только внутри Company.
- User может иметь несколько ролей через `UserRoleAssignment`.
- Допустимые роли: `SYSTEM_OWNER`, `OPERATIONS_MANAGER`, `TECHNICIAN`, `VIEWER`.
- Scalar `user.role` не используется.
- Доступ к локациям хранится через `UserLocationAccess`.
- Backend-операции с автомобилями обязаны ограничиваться Company пользователя и разрешёнными локациями.
- `SYSTEM_OWNER` может просматривать пользователей своей Company, управлять ролями, `UserLocationAccess` и CRUD `Location`/`Site`, включая изменение собственных location access.
- `OPERATIONS_MANAGER` может просматривать пользователей своей Company, управлять ролями других пользователей кроме назначения/снятия `SYSTEM_OWNER`, управлять `UserLocationAccess` других пользователей и CRUD `Location`/`Site`; собственные роли и location access изменять нельзя.
- `TECHNICIAN` работает только в назначенных Location/Site и не имеет административных прав.
- `VIEWER` имеет только чтение в рамках назначенных Location/Site и не имеет административных прав.
- Role restrictions задаются декларативно; `JwtAuthGuard` и company/location scope остаются обязательными.
- Пользователь обязан иметь хотя бы одну роль; пустой и содержащий дубликаты набор отклоняется с `400`.
- В каждой Company должен оставаться хотя бы один `SYSTEM_OWNER`; снятие роли у последнего владельца возвращает `409`.
- `SYSTEM_OWNER` может менять любые роли, включая собственные, если после операции остаётся другой `SYSTEM_OWNER`.
- `OPERATIONS_MANAGER` может просматривать роли и менять роли других пользователей, но не может назначать или снимать `SYSTEM_OWNER`.
- Замена ролей полностью заменяет `UserRoleAssignment` и удаляет все `AuthSession` пользователя одной транзакцией.
- Access token действует 7 минут и не инвалидируется досрочно; после удаления сессий refresh невозможен.
- Refresh flow читает актуальные `isActive` и роли пользователя из БД.
- При отключении пользователя `isActive` устанавливается в `false`, а все его `AuthSession` удаляются; `authVersion`/`tokenVersion` не используется.

## 3.1. Location и Site

- Административные write-операции доступны `SYSTEM_OWNER` и `OPERATIONS_MANAGER`.
- Location и Site не удаляются физически; деактивация устанавливает `isActive = false`.
- Активные и неактивные Location/Site разрешено просматривать и редактировать.
- Site разрешено создавать как в активной, так и в неактивной Location.
- Location разрешено деактивировать только при отсутствии автомобилей на её текущих площадках.
- Site разрешено деактивировать только при отсутствии автомобилей с этой текущей площадкой.
- Наличие Sites и `UserLocationAccess` не блокирует деактивацию Location.
- Неактивные Location/Site сохраняются для истории, но не используются в новых Arrival, назначениях автомобилей и новых бизнес-операциях.
- Код Location уникален в Company; название Site уникально в Location.
- Чужая или отсутствующая Location/Site возвращается административному API как `404`.

## 4. Lifecycle автомобиля

| Статус     | Значение                                                    |
| ---------- | ----------------------------------------------------------- |
| `ACTIVE`   | Автомобиль находится в операционном контуре.                |
| `ISSUED`   | Автомобиль выдан.                                           |
| `ARCHIVED` | Автомобиль выведен из активного учёта без удаления истории. |

Допустимые переходы:

- создание автомобиля → `ACTIVE`;
- `ACTIVE` → `ISSUED` при успешной выдаче;
- `ISSUED` → `ACTIVE` при возврате;
- `ACTIVE` → `ARCHIVED` при архивировании;
- `ARCHIVED` → `ACTIVE` при восстановлении.

`ARRIVED`, `PSO` и `READY` не являются lifecycle-статусами.

## 5. PSO

- PSO хранится отдельно от lifecycle в one-to-one relation `Car` → `Pso`.
- Допустимые статусы PSO: `PENDING`, `COMPLETED`.
- Завершение PSO фиксирует `completedOn`, `completedById` и событие `PSO_COMPLETED`.
- Повторное открытие переводит PSO в `PENDING`, очищает данные завершения и фиксирует `PSO_REOPENED`.
- Завершение или повторное открытие PSO не меняет `CarLifecycleStatus`.
- Выдача автомобиля разрешена только при `Pso.status = COMPLETED`.
- Pso создаётся во время приёмки автомобиля со статусом `PENDING`.
- Обязательный `deadlineOn` рассчитывается как `arrivedOn + 3` календарных дня.

## 6. Выдача и возврат

- Выдача разрешена только для `ACTIVE` автомобиля.
- Заблокированный автомобиль выдавать нельзя.
- До выдачи PSO должен быть завершён.
- Выдача создаёт `VehicleIssue`, переводит Car в `ISSUED` и создаёт событие `CAR_ISSUED`.
- Повторная выдача без возврата запрещена.
- Возврат заполняет данные возврата в актуальной `VehicleIssue`, переводит Car в `ACTIVE`, обновляет площадку и создаёт событие `CAR_RETURNED`.
- Связь выдачи с `DeliveryAppointment` опциональна.

## 7. BatteryCheck и задачи

Подтверждено:

- `BatteryCheck` хранит факт выполненной проверки: Car, исполнителя, серверную дату и необязательные voltage/comment.
- График начинается от `Car.arrivedOn`; первая плановая дата — `arrivedOn + 30` календарных дней, следующие даты — `arrivedOn + 30 × N`.
- Фактическая дата `BatteryCheck` не сдвигает календарный график.
- Проверку разрешено выполнить начиная за 3 календарных дня до плановой даты и позднее.
- Одна запись `BatteryCheck` закрывает ровно один, самый старый незакрытый период. Несколько просроченных периодов закрываются последовательными проверками.
- Текущий период определяется количеством уже созданных `BatteryCheck`; отдельная persistent-сущность планирования не используется.
- Статус `UPCOMING` применяется за 2–3 дня до срока, `URGENT` — за 1 день и в плановую дату, `OVERDUE` — после плановой даты.
- `GET /cars/tasks` возвращает незавершённый PSO и текущую Battery-задачу доступных активных автомобилей.
- Dashboard считает Battery-метрики `Upcoming`, `Urgent` и `Overdue` по тем же правилам.
- Legacy-поле `nextBatteryCheckAt` не используется.

## 8. История и удаление

- Car не удаляется физически в штатном бизнес-процессе.
- Изменения lifecycle и ключевые операции фиксируются через `VehicleEvent`.
- Архивирование используется вместо удаления автомобиля.

## 9. Персонал и временные пароли

- `SYSTEM_OWNER` создаёт пользователей с любыми существующими ролями и сбрасывает пароль любому другому активному пользователю своей Company.
- `OPERATIONS_MANAGER` создаёт только single-role `TECHNICIAN` и сбрасывает пароль только такому пользователю.
- Новый сотрудник обязательно получает минимум одну активную Location своей Company; дубликаты и недоступные локации отклоняются.
- Временный пароль задаётся администратором, содержит минимум шесть латинских букв/цифр, минимум одну букву и одну цифру.
- Административно созданный пользователь получает `mustChangePassword = true`.
- Новый пароль не может совпадать с временным; сравнение выполняется через bcrypt.
- До первичной смены разрешены только `me`, `refresh`, `logout` и `change-initial-password`; остальные защищённые API возвращают `PASSWORD_CHANGE_REQUIRED`.
- Успешная смена пароля снимает флаг, удаляет старые refresh-сессии и создаёт новую.
- Административный reset запрещён для самого себя и неактивного пользователя, устанавливает новый временный hash, включает флаг и удаляет все refresh-сессии.
- Старый access token после смены ролей, reset или отключения может действовать максимум оставшиеся семь минут.
- Username сотрудника хранится после trim/lowercase и соответствует `^[a-z0-9._-]{3,32}$`.
- Имя и фамилия содержат 1–64 символа: кириллица, латиница, пробел или дефис.
- `SYSTEM_OWNER` редактирует, активирует и деактивирует любого пользователя своей Company.
- `OPERATIONS_MANAGER` выполняет эти операции только для single-role `TECHNICIAN` с общей Location и не управляет собой.
- Deactivate запрещён для самого себя и последнего активного `SYSTEM_OWNER`; роли, location access и история сохраняются, сессии удаляются.
- Activate разрешён только для неактивного пользователя и требует новый временный пароль; старый пароль становится недействителен.
- При замене location access менеджер изменяет только назначения в пределах собственного scope, сохраняя внешние назначения техника.
- Активный пользователь не может остаться без назначенной Location.
