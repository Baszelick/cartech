# CarTech AI Development Guide

> Этот документ обязателен для любого AI-агента, работающего над проектом CarTech.

Цель агента:
помогать развивать проект как коммерческое Enterprise-приложение, сохраняя архитектуру, читаемость и управляемость кода.

---

# Project Overview

CarTech — система управления автомобильной площадкой дилерского центра.

Основные процессы:

- приемка автомобилей;
- хранение автомобилей;
- работа с площадками и локациями;
- предпродажная подготовка (ПСО);
- контроль аккумуляторов;
- выдача автомобилей;
- история операций.

Проект развивается как pet-project с архитектурой, приближенной к реальным Enterprise-системам.

Главные цели:

- читаемый код;
- предсказуемая архитектура;
- понятные доменные модели;
- отсутствие скрытой магии;
- постепенное развитие без больших переписываний.

# Architecture

Проект использует модульную слоистую архитектуру.

Основная схема:


Controller

↓

Service

↓

Prisma / Data Access


---

## Controller

Controller отвечает только за:

- получение запроса;
- валидацию через DTO;
- вызов сервиса;
- возврат ответа.

Controller НЕ содержит:

- бизнес-правила;
- расчёты;
- работу с Prisma.

---

## Service

Service содержит бизнес-логику.

Правила:

- один метод = одна бизнес-операция;
- большие методы необходимо разбивать;
- сложная логика выносится в private методы.

---

## Prisma

Prisma используется только внутри backend слоя.

Запрещено:

- обращаться к Prisma из Controller;
- возвращать Prisma Entity напрямую наружу;
- использовать старые поля после изменения Schema.

# Development Rules

## SOLID

Следовать принципам SOLID.

---

## KISS

Не усложнять решение без необходимости.

Не создавать абстракции заранее.

---

## DRY

Не дублировать код.

Но не создавать универсальные сервисы только ради удаления нескольких строк.

---

## Readability First

Читаемость важнее краткости.

Предпочитать:

```ts
validateArrivalAccess()
createVehicle()
updateStatus()

вместо:

execute()
process()
handle()
Task Execution Rules

Каждая задача должна быть небольшой и изолированной.

Перед изменением:

Изучить Prisma Schema.
Проверить существующие DTO.
Проверить текущий endpoint.
Проверить документацию.
Определить влияние изменения.

Запрещено:

переписывать весь модуль без необходимости;
менять несколько доменных областей одновременно;
добавлять новые бизнес-правила без подтверждения;
исправлять архитектуру "заодно".
Legacy Migration Rules

В проекте могут существовать старые части кода.

При миграции:

Правильный порядок:

Определить актуальный контракт.
Проверить Prisma модель.
Мигрировать один endpoint.
Обновить тесты.
Удалить старую логику.

Запрещено:

добавлять новый код поверх старой модели;
возвращать удалённые поля ради компиляции;
сохранять устаревшую архитектуру без причины.
DTO Rules

DTO используются всегда для API.

Правила:

Request DTO для входящих данных;
Response DTO для ответов;
Prisma Entity не являются API контрактом.
Validation

Использовать:

class-validator;
class-transformer.

Не делать ручную проверку данных там, где достаточно DTO validation.

Database Rules

Prisma Schema является источником истины.

Перед изменением backend логики:

проверить:

модели;
relations;
enum;
обязательность полей.

Изменения базы:

только через Prisma migrations.

Запрещено:

менять структуру базы вручную;
придумывать отсутствующие поля;
использовать устаревшие relations.
Transactions

Если операция меняет несколько сущностей:

использовать:

prisma.$transaction()

Особенно:

приемка автомобилей;
изменение связанных сущностей;
массовые операции.
Testing Rules

Новый endpoint должен иметь:

service test;
controller test.

Проверять:

успешный сценарий;
NotFound;
Forbidden;
Conflict;
основные бизнес-правила.

Тесты должны фиксировать контракт.

Не писать тесты только ради покрытия.

Frontend Rules

Использовать:

Standalone Components;
Signals;
OnPush.

Запрещено:

NgModules для новых компонентов;
any без причины;
слабая типизация.
UI Library

Использовать существующие UI-компоненты.

Например:

ct-button;
ct-input;
ct-select;
ct-icon;
ct-form-field.

В бизнес-интерфейсах не использовать обычные:

<input>
<select>
<textarea>
<button>

если существует компонент библиотеки.

Styling

Использовать SCSS.

Использовать дизайн-систему проекта:

var(--space-16)
var(--radius-8)
var(--text-14)

Избегать magic numbers.

Error Handling

Использовать стандартные NestJS исключения:

BadRequestException;
NotFoundException;
ConflictException;
ForbiddenException;
UnauthorizedException.
Business Rules

Бизнес-логика находится только в сервисах.

Не размещать её:

в Controller;
в DTO;
в Prisma Schema.

Если бизнес-правило неизвестно:

НЕ придумывать.

Нужно:

создать TODO;
описать требующее решения место.
Documentation Rules

Документация должна оставаться компактной.

Не создавать новые документы без необходимости.

Использовать:

docs/

README.md
ARCHITECTURE.md
DOMAIN.md
BUSINESS_RULES.md
DATABASE.md
API.md
ROLES.md
ROADMAP.md
DECISIONS.md
AGENTS.md
Work Report

После каждой задачи давать короткий отчёт:

Completed:
- ...

Changed:
- ...

New TODO:
- ...

Blockers:
- ...

Не писать длинные описания изменений.

Final Goal

Цель проекта:

создать код, который можно показать как пример Enterprise-разработки.

Приоритеты:

Архитектура.
Читаемость.
Поддерживаемость.
Корректная бизнес-логика.
Скорость разработки.
