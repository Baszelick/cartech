# Architecture Decisions

## 2026-08-03 — Company code, login contract и единый environment

Принято:

- `Company.code` — обязательный глобально уникальный публичный код: trim, uppercase, длина 2–32, формат `^[A-Z0-9_-]{2,32}$`.
- Login принимает `companyCode`, `username` и `password`; внутренние relations, JWT и scope продолжают использовать UUID `companyId`.
- Отсутствующая/неактивная Company, отсутствующий/неактивный User и неверный пароль возвращают одинаковый `401`.
- Nest, Prisma CLI и seed загружают единственный локальный `/.env`; безопасный шаблон находится в `/.env.example`.
- `GET /company/me` возвращает публичные поля компании из `companyId` JWT.
- Стартовая Company — `Форсаж` (`FORSAGE`), владелец — `ivan` Иван Талисов с ролью `SYSTEM_OWNER`.

> Документ содержит все важные архитектурные решения проекта.
>
> Каждое решение описывает:
>
> - проблему;
> - принятое решение;
> - причину;
> - последствия.

# ADR-001

## Использование собственной UI-библиотеки

### Статус

✅ Принято

### Проблема

Использование компонентов различных UI-библиотек приводит к разному поведению элементов, усложняет поддержку и затрудняет изменение дизайна.

### Решение

Создать собственную UI-библиотеку компонентов.

Все элементы интерфейса строятся только на собственных компонентах.

Например:

- ct-button
- ct-input
- ct-select
- ct-date-picker
- ct-form-field
- ct-icon

### Причина

- единый внешний вид;
- полный контроль поведения;
- отсутствие зависимости от сторонних UI Kit;
- возможность быстро менять дизайн всей системы.

### Последствия

Любая новая форма должна использовать только компоненты библиотеки.

Использование обычных HTML input, select и textarea запрещено.

# ADR-002

## Использование Angular Signals

### Статус

✅ Принято

### Проблема

Большая часть состояния приложения локальна и не требует полноценного глобального Store.

### Решение

Основным способом хранения состояния являются Angular Signals.

RxJS используется только там, где необходима работа с потоками данных.

### Причина

- меньше шаблонного кода;
- проще читать;
- выше производительность;
- современный подход Angular.

### Последствия

Signals используются по умолчанию.

NgRx подключается только при реальной необходимости.

# ADR-003

## Автомобиль хранит только Model

### Статус

⛔ Заменено ADR-011

### Проблема

Бренд можно хранить двумя способами.

Вариант 1

```
Car

↓

brandId

↓

modelId
```

Вариант 2

```
Car

↓

modelId

↓

Brand определяется через Model
```

### Решение

Использовать второй вариант.

Car хранит только modelId.

Brand определяется через связь модели.

### Причина

Исключается дублирование данных.

Невозможно получить ситуацию:

```
Brand = Jetour

Model = BMW X5
```

### Последствия

Brand никогда не хранится в таблице Car.

# ADR-004

## Приемка автомобилей выполняется одной транзакцией

### Статус

⛔ Заменено ADR-010

### Проблема

Во время приемки необходимо создать:

- Arrival;
- несколько Car.

При ошибке создания одного автомобиля данные могут оказаться неконсистентными.

### Решение

Использовать Prisma Transaction.

```
Arrival

↓

Cars
```

создаются внутри одной транзакции.

### Причина

Сохранение целостности данных.

### Последствия

При любой ошибке откатывается вся операция.

# ADR-010

## Приёмка является бизнес-операцией, а не отдельной сущностью

### Статус

✅ Принято

### Контекст

Legacy-модель содержала отдельную сущность `Arrival`. В актуальной Prisma Schema её нет: факт приёмки хранится на `Car` через `arrivedOn` и `arrivalSiteId`, а в истории предусмотрено событие `CAR_ARRIVED`.

### Решение

В целевой модели отдельная сущность `Arrival` не используется.

Приёмка — атомарная бизнес-операция, которая:

- создаёт один или несколько `Car`;
- фиксирует `arrivedOn` и `arrivalSiteId`;
- фиксирует создавшего пользователя;
- создаёт для каждого `Car` отдельную `Pso` со статусом `PENDING` и `deadlineOn = arrivedOn + 3 календарных дня`;
- создаёт для каждого автомобиля `VehicleEvent` типа `CAR_ARRIVED`;
- выполняет все изменения одной транзакцией.

Данные автовоза и отдельный реестр партий не входят в подтверждённый MVP contract.

### Последствия

- legacy `Arrival`, `arrivalId` и endpoints ресурса `/arrivals` не являются целевым contract;
- пользовательский сценарий приёмки сохраняется, но API должен описывать операцию создания автомобилей, а не CRUD сущности Arrival;
- `Car`, связанная `Pso` и `CAR_ARRIVED` создаются атомарно; ошибка любого шага откатывает всю приёмку;
- новая `Pso` не содержит `completedOn`/`completedById`, а Car остаётся в lifecycle `ACTIVE`;
- если потребуется хранить партии или данные автовоза, это оформляется новым ADR до изменения Schema.

# ADR-011

## Brand, Model и Color хранятся как значения автомобиля

### Статус

✅ Принято

### Контекст

ADR-003 и ADR-005 описывали нормализованные справочники `Brand`, `CarModel` и `Color`. Актуальная Prisma Schema хранит `brand`, `model` и `color` непосредственно в `Car`.

### Решение

Целевая MVP-модель использует:

- `brand: String`;
- `model: String`;
- `color: String?`.

Значения являются snapshot-данными автомобиля. Отдельные Prisma entities и relations для Brand, CarModel и Color в MVP не используются.

### Последствия

- legacy `brandId`, `modelId`, `colorId` и связанные relations удаляются из backend contracts;
- корректность пары brand/model обеспечивается входным contract и бизнес-валидацией, а не relation базы;
- административные динамические справочники могут быть добавлены только отдельным решением, если появится подтверждённая потребность.

# ADR-012

## Пользователь может иметь несколько ролей

### Статус

✅ Принято

### Контекст

Legacy Auth использует scalar `user.role`. Актуальная Schema содержит `UserRoleAssignment[]` и уникальную пару `(userId, role)`.

### Решение

Роли хранятся только через `UserRoleAssignment`.

Допустимые роли определяются enum `UserRole`:

- `SYSTEM_OWNER`;
- `OPERATIONS_MANAGER`;
- `TECHNICIAN`;
- `VIEWER`.

Scalar-поле `User.role` не является частью целевой модели. Публичный user contract и JWT должны представлять роли массивом. Company принадлежность берётся из `User.companyId`, доступные локации — из `UserLocationAccess`.

### Минимальная permission matrix MVP

| Возможность                                          | `SYSTEM_OWNER` | `OPERATIONS_MANAGER` | `TECHNICIAN` | `VIEWER` |
| ---------------------------------------------------- | -------------: | -------------------: | -----------: | -------: |
| Просмотр пользователей своей Company                 |             ✅ |                   ✅ |           ❌ |       ❌ |
| Управление ролями других пользователей               |             ✅ |          ✅ ограниченно |           ❌ |       ❌ |
| Управление `UserLocationAccess` других пользователей |             ✅ |                   ✅ |           ❌ |       ❌ |
| Изменение собственного `UserLocationAccess`          |             ✅ |                   ❌ |           ❌ |       ❌ |
| CRUD `Location`/`Site`                               |             ✅ |                   ✅ |           ❌ |       ❌ |

Доступ `TECHNICIAN` и `VIEWER` всегда ограничивается назначениями `UserLocationAccess`; `VIEWER` имеет только чтение. Детальные permissions для остальных бизнес-операций определяются отдельными решениями.

Ограничение `OPERATIONS_MANAGER`: нельзя изменять собственные роли, назначать `SYSTEM_OWNER` или снимать `SYSTEM_OWNER`.

### Последствия

- Auth мигрируется с `role` на `roles`;
- проверки доступа должны учитывать набор ролей, company и location access;
- role restrictions объявляются декларативно через metadata decorator и проверяются общим `RolesGuard`;
- `JwtAuthGuard` остаётся обязательным перед `RolesGuard`;
- ручные проверки ролей в controllers и services не используются;
- отдельная permission entity в MVP не создаётся.

# ADR-013

## Lifecycle автомобиля отделён от рабочих процессов

### Статус

✅ Принято

### Контекст

Legacy-код использует статусы `ARRIVED`, `PSO`, `READY`, `ISSUED`. Актуальная Schema разделяет общий lifecycle, PSO и выдачу.

### Решение

`CarLifecycleStatus` содержит только:

- `ACTIVE` — автомобиль находится в операционном контуре;
- `ISSUED` — автомобиль выдан;
- `ARCHIVED` — автомобиль выведен из активного учёта с сохранением истории.

Приёмка, PSO, блокировка и местоположение не являются lifecycle-статусами:

- приёмка фиксируется полями `arrivedOn`, `arrivalSiteId` и событием;
- PSO хранится в relation `Pso` со статусом `PENDING` или `COMPLETED`;
- блокировка хранится через `isBlocked` и связанные поля;
- перемещение хранится через `currentSiteId` и `VehicleMovement`.

Выдача создаёт `VehicleIssue`, переводит Car из `ACTIVE` в `ISSUED` и фиксирует `CAR_ISSUED`. Возврат закрывает текущую выдачу, возвращает Car в `ACTIVE` и фиксирует `CAR_RETURNED`. Архивирование переводит `ACTIVE` или возвращённый автомобиль в `ARCHIVED`; восстановление переводит `ARCHIVED` в `ACTIVE`.

### Ограничения

- выдача разрешена только для `ACTIVE`, не заблокированного автомобиля с завершённым PSO;
- PSO completion не меняет `CarLifecycleStatus`;
- legacy-статусы `ARRIVED`, `PSO`, `READY` не используются.

# ADR-014

## BatteryCheck хранит факт проверки, календарный график вычисляется от Arrival

### Статус

✅ Принято

### Решение

`BatteryCheck` является журналом выполненных проверок:

- проверка принадлежит одному Car;
- фиксирует исполнителя и дату;
- может содержать voltage и comment;
- запись проверки не является задачей и не хранит срок следующей проверки.

Плановые периоды вычисляются без отдельной persistent-сущности:

- период `N` имеет срок `Car.arrivedOn + 30 × N` календарных дней;
- первая проверка относится к периоду `N = 1`;
- фактическая дата проверки не переносит следующие сроки;
- количество записей `BatteryCheck` определяет число последовательно закрытых периодов;
- одна запись закрывает только самый старый незакрытый период;
- окно выполнения открывается за 3 календарных дня до срока;
- статусы задачи: `UPCOMING` за 2–3 дня, `URGENT` за 1 день и в день срока, `OVERDUE` после срока.

### Последствия

`GET /cars/tasks`, Dashboard и создание `BatteryCheck` обязаны использовать один общий вычислитель графика. Prisma Schema не расширяется: `BatteryCheck` остаётся журналом фактов, а задачи вычисляются из `arrivedOn` и количества проверок.

# ADR-015

## Новая Prisma Schema получает чистую migration history

### Статус

✅ Принято

### Контекст

Существующие migrations создают legacy-модель:

- numeric identifiers;
- `Arrival`, `Brand`, `CarModel`, `Color`;
- scalar `User.role`;
- legacy `CarStatus`.

Актуальная Prisma Schema описывает несовместимую UUID/multi-company модель. Последовательное применение существующих migrations не создаёт структуру текущей Schema, а актуальный seed не может работать поверх их конечного состояния.

Фактическое состояние подключённой PostgreSQL базы и наличие ценных legacy-данных подтвердить не удалось.

### Рассмотренные варианты

1. **Новая база с чистой историей.** Создать initial migration из утверждённой Schema и разворачивать новые dev/test environments с нуля.
2. **Миграция существующей базы.** Написать контролируемый data migration с явным mapping legacy-сущностей в новую модель.
3. **Сохранение legacy migrations как активной истории.** Продолжить добавлять migrations поверх несовместимой схемы.

### Решение

Для целевой разработки выбран вариант 1: новая база с чистой migration history.

Legacy migrations нельзя оставлять в активной цепочке перед новым baseline. До создания baseline они сохраняются без изменений как материал для анализа и не применяются к новой базе.

Вариант 2 используется только если будет подтверждено, что существующие данные необходимо сохранить. Для него нужны backup, инвентаризация данных, mapping и отдельный план проверки.

Вариант 3 отклонён: он не даёт воспроизводимого развёртывания текущей Schema.

### Последствия

- clean baseline создан как `prisma/migrations/migration_init`;
- legacy history перенесена в `prisma/legacy-migrations` и исключена из active migration path;
- `prisma migrate deploy` применяется только к новой или явно подготовленной базе;
- существующая legacy database не обновляется этим baseline поверх старой структуры;
- фактический database drift должен проверяться через direct PostgreSQL connection, не через pooler.

# ADR-016

## Location и Site используют soft-deactivation

### Статус

✅ Принято

### Решение

- физическое удаление Location и Site не используется;
- деактивация устанавливает `isActive = false`;
- активные и неактивные сущности можно просматривать и редактировать;
- Site можно создавать внутри неактивной Location;
- Location можно деактивировать только при отсутствии автомобилей на её текущих площадках;
- Site можно деактивировать только при отсутствии автомобилей с этой `currentSite`;
- Sites и `UserLocationAccess` сохраняются и не блокируют деактивацию Location;
- неактивные сущности остаются в истории, но исключаются из новых Arrival, назначений и бизнес-операций.

### Последствия

Деактивация выполняется транзакционно и возвращает `409 Conflict`, если текущие автомобили препятствуют операции. Prisma Schema не изменяется: существующего поля `isActive` достаточно.

# ADR-017

## Замена ролей инвалидирует refresh-сессии

### Статус

✅ Принято

### Решение

- пользователь всегда имеет хотя бы одну уникальную роль;
- в каждой Company сохраняется минимум один `SYSTEM_OWNER`;
- `SYSTEM_OWNER` управляет любыми ролями и может снять собственную роль владельца только при наличии другого владельца;
- `OPERATIONS_MANAGER` управляет ролями других пользователей, но не назначает и не снимает `SYSTEM_OWNER`;
- полная замена `UserRoleAssignment` и удаление всех `AuthSession` целевого пользователя выполняются одной serializable transaction;
- access JWT живёт 7 минут и продолжает работать до истечения срока;
- refresh и следующий login читают актуальные роли и `isActive` из БД;
- `authVersion`/`tokenVersion` и database lookup на каждом защищённом запросе не используются.

### Последствия

Изменение ролей немедленно запрещает получение нового access token через существующие refresh tokens. Старый access token может сохранять прежние роли не более 7 минут.

# ADR-018

## Контракт идентификаторов автомобиля

### Статус

✅ Принято

### Решение

- `shortVin` — обязательный редактируемый рабочий идентификатор из шести символов `A-Z0-9`;
- входной `shortVin` нормализуется через trim и uppercase;
- совпадения `shortVin` разрешены и не блокируют операции;
- API возвращает `hasShortVinDuplicate`, учитывая только другие автомобили той же Company;
- полный `vin` необязателен, редактируем и может быть очищен через `null`;
- заполненный VIN нормализуется через trim и uppercase и соответствует `^[A-HJ-NPR-Z0-9]{6,17}$`;
- буквы `I`, `O`, `Q` запрещены; дополнительная структурная проверка 17-символьного VIN не выполняется;
- заполненный VIN уникален в пределах Company, а одинаковые VIN разных Company допустимы.

### Последствия

`Car.vin` nullable, composite unique `(companyId, vin)` сохраняется, а `(companyId, shortVin)` индексируется без unique constraint. Arrival, Car list/details и `PATCH /cars/:id` используют единый контракт и warning flag.

# ADR-019

## Временный пароль и обязательная первичная смена

### Статус

✅ Принято

### Решение

- административно созданный пользователь получает `mustChangePassword = true`;
- временный и новый пароль соответствуют `^(?=.*[A-Za-z])(?=.*\d)[A-Za-z\d]{6,}$`;
- пользователь до смены пароля имеет доступ только к `/auth/me`, `/auth/refresh`, `/auth/logout` и `/auth/change-initial-password`;
- ограничение выполняется централизованно после JWT-аутентификации;
- смена временного пароля удаляет старые `AuthSession`, создаёт новую refresh-сессию и возвращает новые токены;
- административный reset снова устанавливает `mustChangePassword = true` и удаляет все refresh-сессии;
- уже выпущенный access token может действовать не более оставшихся семи минут.

### Последствия

Refresh flow всегда читает актуальный флаг из базы. Флаг включается в auth response и access-token context, но refresh-token остаётся HttpOnly и не читается клиентским JavaScript.

# ADR-020

## Lifecycle сотрудника и location scope менеджера

### Статус

✅ Принято

### Решение

- `SYSTEM_OWNER` управляет lifecycle и полным набором Location любого пользователя своей Company.
- `OPERATIONS_MANAGER` управляет только single-role `TECHNICIAN`, с которым имеет минимум одну общую Location, и никогда не управляет собой.
- менеджер заменяет только назначения внутри собственного location scope; назначения техника вне scope сохраняются;
- активный пользователь не может остаться без Location;
- deactivate сохраняет роли, Location и историю, но удаляет все `AuthSession`;
- activate требует новый временный пароль, включает `mustChangePassword` и удаляет старые сессии;
- username нормализуется через trim/lowercase и соответствует `^[a-z0-9._-]{3,32}$`.

### Последствия

Прямая связь technician → manager не нужна: право управления выводится из ролей и пересечения `UserLocationAccess`.
